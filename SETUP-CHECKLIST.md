# Saga — Infra Setup Checklist

Tracks the m920q build-out, step by step. Update this file as steps complete so any session (or Claude instance) can see where things stand.

## Decision: Proxmox VE on bare metal, Ubuntu LXCs for the workloads

Brandon's R730 (`r730-proxmox`) is a work machine and stays out of this entirely — Saga gets its own hypervisor on the m920q. Proxmox on bare metal.

**Guest type: LXC, not VM.** This box is planned to eventually run more than just Saga — Plex (GPU transcoding, migrating over from an existing server, likely a few months out) and possibly a GPU-backed local voice/LLM layer for home automation later — alongside Saga's own Docker stack today. A single consumer GPU can only be PCI-passed-through to **one** VM at a time (no vGPU/SR-IOV on this card), which would force everything into one VM anyway and defeat the point of separating them. LXC containers instead bind-mount the host's `/dev/nvidia*` device nodes rather than claiming exclusive PCI ownership, so **multiple LXCs can share the one physical GPU concurrently** — same as multiple processes sharing a GPU on bare metal. No IOMMU/VFIO, no PCI passthrough reset bugs either. Deciding this now, even though Plex is later, avoids painting ourselves into a VM-only corner.

**Immediate scope: just the `saga` LXC.** Plex is a separate future integration (existing Plex server, migrating in a few months — not part of this build) and gets its own LXC when that time comes, sharing the same GPU device-node bind-mount pattern. Not tracked as a step below yet.

**Known caveat for later, not a blocker today:** GeForce drivers cap concurrent NVENC transcode sessions at 3 (unlike Quadro/datacenter cards), and the 6GB VRAM pool is shared — once Plex and Ollama are both running, a larger loaded model plus multi-stream transcoding could contend for VRAM. Worth watching once both are live.

**Two new gotchas hit and fixed, beyond what's in STACK-FOUNDATION.md's own known issue:**

1. **`host.docker.internal` resolving is not the same as being reachable.** Even after the `extra_hosts: host-gateway` fix makes the hostname resolve (to the `docker0` bridge gateway, e.g. `172.17.0.1`), a Postgres port published as `127.0.0.1:5432:5432` is still unreachable from other containers — that binding only accepts connections from the literal host loopback, not the bridge gateway address other containers use to reach "the host." This is a Docker Desktop vs. native Docker Engine networking difference: works fine on Desktop, silently fails on Linux Engine. Fix: publish as `5432:5432` (all interfaces) instead. Mitigated by strong password auth and this box being LAN/Tailscale-only, not internet-facing.
2. **`prisma migrate dev` needs `CREATEDB`**, which the locked-down app role deliberately doesn't have (by design, per STACK-FOUNDATION.md's two-role split). Fix: added a separate `shadowDatabaseUrl` in `schema.prisma` pointing at the Postgres **superuser** credentials — Prisma uses this only to build/tear down its temporary shadow database for schema diffing at migration time; the running app never uses it. `prisma migrate deploy` (production path) doesn't need this at all.
3. **`docker compose restart` does not pick up new `.env` values** — the container keeps whatever environment it was created with. After changing `.env` (e.g. adding `SHADOW_DATABASE_URL`), the container needs `up -d --force-recreate`, not just `restart`.

## Date/timezone bug fix + reminder-cadence rework (done 2026-09-19, same day)

Brandon reported the People page's birthday reminder showing "September 10th" for a birthday actually stored as the 11th, and no clear "this is the birthday date" label anywhere.

- [x] **Root cause confirmed:** `nextAnnualOccurrence()` (`saga-web/src/shared/lib/dates.ts`) read a UTC-midnight birthday with **local-timezone** getters (`.getMonth()`/`.getDate()`). For anyone in a timezone behind UTC, UTC midnight on the 11th is still the evening of the 10th locally, so the extracted day was silently off by one. Same class of bug was present in `computeFireDates()`/`regenerateForNextYear()` (`saga-api/src/modules/reminders/service.ts`, local `setDate`/`setFullYear`) and in every `toLocaleDateString()` call rendering a birthday/reminder date without `timeZone: "UTC"`.
- [x] **Fixed at the source, not just patched:** `Person.birthday` and `ReminderCascade.anchorDate` are now `@db.Date` (pure SQL date, no time component at all) instead of `DateTime`. All date math (`nextAnnualOccurrence`, `computeFireDates`, `regenerateForNextYear`) now uses UTC getters/setters exclusively; all display code uses a shared `formatDateOnly()` helper that forces `timeZone: "UTC"`.
- [x] **Architecture gap closed:** a `CalendarEvent` and its `ReminderCascade` used to be two separate records linked only by a matching title — not a real relationship, and not how Google Calendar actually models "an event with a list of reminder offsets." Added `ReminderCascade.calendarEventId` (FK to `CalendarEvent`) and `CalendarEvent.isAllDay` (birthdays have no time-of-day). The birthday button now creates the event and links the cascade to it in one flow.
- [x] **Reminder cadence UX now matches Google's own picker:** the Reminders page's single preset dropdown became a checkbox grid of the same offsets Google Calendar offers (1 month/3 weeks/2 weeks/1 week/3 days/1 day/day-of) — check off however many you want. Both the People and Calendar pages now show the chosen cadence in plain English (e.g. "Reminds: 1 month, 3 weeks, 2 weeks, 1 week, 3 days before + day-of"), and the ntfy push text itself now includes the date (e.g. "Jess's birthday — Sep 11") instead of just the bare title.
- [x] **Jess's existing (buggy) birthday reminder was corrupted data from before this fix** — anchored to Sep 10 with a stray 4am-UTC time artifact. Deleted and recreated through the fixed flow; confirmed via direct API calls that the new cascade anchors correctly on Sep 11 with clean midnight-UTC instances, and is now properly linked to its calendar event via the new FK.

## Three real bugs fixed same day, right after the pixel-icon integration

Brandon reported three separate problems after using the app for real: dark mode only changed form field colors (not backgrounds/text), the new achievement/goal icons showed as broken images, and almost nothing in the app could be edited after creation — only added or deleted.

- [x] **Dark mode bug — root cause: `tailwind.config.js` isn't bind-mounted into the dev container** (same class of gotcha as `package.json` needing a real rebuild, see Phase 1's gotchas above). My `darkMode: "class"` edit landed on the LXC host filesystem but the running container kept using the OLD config baked into its image, so Tailwind silently fell back to its default `media`-query-based dark mode — meaning `dark:` utility classes were driven by the browser's OS-level color scheme, completely ignoring the actual toggle/`.dark` class on `<html>`. Only the hand-written plain-CSS `.dark input {...}` rule in `index.css` responded to the real toggle, since that's not Tailwind-generated and doesn't depend on the stale config. Fixed with a real `docker compose ... up -d --build` to bake in the current config; verified via `document.documentElement.className` + computed background-color in both directions before/after toggling, not just visually.
- [x] **Broken icons — root cause: `saga-web/public/` isn't bind-mounted either.** Same underlying issue as the tailwind config, different symptom: image requests to `/icons/...` returned HTTP 200 but with `Content-Type: text/html` (Vite's SPA fallback silently serving `index.html` for a path it couldn't find in its own filesystem, since the icon files only existed on the LXC host, not inside the container). Fixed by adding `./public:/app/public` to `saga-web/docker-compose.dev.yml`'s volumes and recreating the container. Lesson for next time: **any new top-level directory referenced by the frontend (not just individual files) needs its own volume line** — bind mounts aren't recursive-by-convention the way a naive read of "the src folder is mounted" might suggest.
- [x] **Can't edit anything — real, broad gap, not a bug in existing code.** Projects/Checklists/Goals/Calendar/Reminders/People/Finance/Investments/Recipes could all be created and deleted but not edited — most modules had no `PATCH` support at all, or only a narrow one (e.g. transactions could only have their category changed, not merchant/amount). Added full edit support across the board:
  - A shared `InlineEditText` component (`shared/components/InlineEditText.tsx`) — click text to edit, Enter/blur saves, Escape cancels — used for every plain-text field (names, titles, notes, descriptions, merchant names, amounts).
  - New backend `PATCH` endpoints: checklists (rename) + checklist items (edit title, separate from the existing toggle endpoint), calendar events (full edit), reminder cascades (title/anchor/cadence — **regenerates only unsent instances**, already-sent ones stay as historical record), finance accounts/categories/subscriptions/transactions (transactions previously could only have `categoryId` patched), investment accounts, gift ideas (previously status-only).
  - Structured-field entities (calendar events, reminder cascades, recipes) got a proper expand-to-edit-form pattern instead of inline text, since they have real form controls (datetime pickers, cadence checkboxes) that don't fit a single editable text span.
  - Also fixed two pre-existing TypeScript errors in `people/service.ts` (a `Prisma.InputJsonValue` cast issue on `Person.preferences` that had been showing up in every `saga-api` typecheck since Phase 3 — harmless at runtime, but noise worth clearing since the file was already open for this pass).
- [x] Verified thoroughly: every new `PATCH` endpoint smoke-tested directly via the API (create → edit → delete, disposable data cleaned up after each), plus a live browser click-through of the `InlineEditText` UX on a real project (click → type → Enter-to-save and blur-to-save both confirmed persisting server-side, Escape-to-cancel confirmed **not** persisting). One testing-only gotcha hit and resolved, not a product bug: the browser automation tool's `key` action needs the exact string `"Enter"`, not `"Return"` — the latter silently doesn't map to a `KeyboardEvent.key === "Enter"` in that tool, unrelated to how a real browser handles a physical Enter keypress.

## Multi-line inline editing + recipe allergens (added 2026-09-20)

Brandon flagged three more things right after using the new edit-everywhere feature: the description edit box was a single line ("as large as the text... or at least 6 lines minimum"), pressing Enter on mobile submitted instead of adding a newline, and asked for an explicit Save button. Separately: recipes needed a real allergen list, not just a single "contains dairy" flag, with an eye toward eventually sharing recipes with other people (who'd have different allergies) — even just by email.

- [x] **`InlineEditText` reworked** — `as="textarea"` now renders at `Math.max(6, lineCount + 1)` rows (grows with content, minimum 6) instead of a fixed 2-row box. Removed save-on-blur entirely (it raced against clicking a Cancel button — blur fires before the click lands, saving before the cancel registers) in favor of explicit **Save**/**Cancel** buttons shown while editing, on both the single-line and multi-line variants. Single-line (`as="input"`, the default) still saves on Enter, since that's correct there; multi-line never treats Enter as submit — it's a plain textarea, so Enter always just inserts a newline, exactly like normal text-editing behavior, mobile keyboards included.
- [x] Applied `as="textarea"` to every description/notes-style field that had the same one-line, Enter-submits bug: Project description, Goal description, Person notes.
- [x] **`Recipe.containsDairy` (boolean) replaced with `Recipe.allergens` (`String[]`)** — a freeform tag array rather than a fixed enum, per Brandon's explicit direction: he eventually wants a local Ollama pass to scan ingredients and auto-tag allergens, and wants adding a brand-new allergen category later to trigger a re-scan of every saved recipe for it — neither of which should require a schema migration if the underlying field is just a string array. The web UI offers the 9 FDA major allergens (Milk, Eggs, Fish, Shellfish, Tree Nuts, Peanuts, Wheat, Soy, Sesame) + Coconut as quick-toggle checkboxes (`shared/lib/allergens.ts`), plus a free-text field for anything else. The recipe list's filter row is built from whatever allergens are actually in use across saved recipes (the common list plus any custom ones), not just the fixed checkbox set.
  - **Not built yet, deliberately**: the actual Ollama ingredient-scanning and retroactive re-tagging Brandon described. That's real new work (an ingredient-analysis pass through the local model, plus a batch job to re-run it against existing recipes when a new allergen is added) — flagged for a future pass, not bundled into this one.
  - Migration gotcha: `prisma migrate dev` refuses to run non-interactively at all (even with `--create-only`) once it detects a data-loss warning (dropping a column with existing rows) — there's no accept-flag for `migrate dev` itself (unlike `db push`). Worked around by hand-writing the migration SQL directly into `prisma/migrations/<timestamp>_name/migration.sql` and applying it with `prisma migrate deploy`, which doesn't have the interactive gate. Also hit a permissions snag doing this: the `migrations/` folder is owned by `root` on the LXC (since earlier `migrate dev` runs happened inside the container as root, and it's bind-mounted), so creating a new migration folder from the host needed `sudo mkdir` + `chown` first.
- [x] **Brandon's eventual goal — sharing recipes with others, even just by email** — explicitly deferred ("eventually"), not built now. Noted here so it isn't lost: worth a proper look once it's actually wanted (options range from a simple "export as text" / print view up through a shareable read-only link).
- [x] Verified: both `tsc --noEmit` clean; the migration applied cleanly against the one real recipe row that existed (`containsDairy: false` → `allergens: []`, no data implied lost); a live browser pass confirmed the textarea/Save/Cancel UX on both desktop and mobile viewport sizes, and confirmed Recipes' edit button opens a fully pre-filled form.

## AI task routing + Inbox ("dumping ground") + recipe photo/voice capture (added 2026-09-20)

The biggest feature pass yet — planned properly in Plan Mode given the size (see the approved plan for full design detail). Ties the Ollama instance (running since infra setup, never actually called from code until now) into the app for real, adds a Settings page to pick which model handles which AI task, and adds an "Inbox" quick-capture page: paste text or upload a photo/recording, review the AI's proposed structured item, edit it if needed, and only on explicit confirm does it get created — reject it with feedback and it re-tries using the original input plus every prior attempt, not a blind restart.

- [x] **AI client layer** (`saga-api/src/lib/ai/`) — `ollama.ts`/`claude.ts` call the two model providers directly (no SDK dependency for Claude, plain `fetch`), `tesseract.ts`/`ffmpeg.ts` shell out to local CLI tools, `whisper.ts` calls the new transcription service, `taskRunner.ts` is the single dispatch point every feature goes through, keyed by a freeform `taskKey` so which model runs a task is a per-user Settings row, not hardcoded.
- [x] **New `AiTaskSetting` + `InboxEntry` models**, plus `Recipe.sourceImagePaths`/`sourceMediaPaths`/`sourceTranscript` for keepsake media. `InboxEntry.attempts` (JSON array of `{proposal, userFeedback}`) is what makes reject-and-retry actually informed rather than starting cold each time.
- [x] **Recipe photos**: two switchable strategies in Settings — `direct_vision` (a vision model reads the card straight into structured JSON; the right tool for actual handwriting) and `ocr_then_structure` (Tesseract OCR → `llama3.1:8b` cleans it up; fully local, but scoped to printed/typed cards only — verified honestly via research that both Tesseract and Docling "fail hard" on real handwriting, so this path doesn't try to be a handwriting solution). Supports front+back of the same card as one capture.
- [x] **Recipe voice/video**: a new standalone service, **`saga-whisper`** (own Dockerfile, FastAPI + faster-whisper, CPU-only for this pass since transcription is an occasional batch job not worth contending with Ollama for the box's 6GB VRAM), transcribes a recording; `ffmpeg` pulls the audio track first if it's a video. The structuring prompt explicitly preserves imprecise/informal phrasing ("a good glug of oil") instead of inventing false measurements — verified this actually holds up in testing (see gotchas below).
- [x] **Inbox target-type registry** (`modules/inbox/targetTypes.ts`) reuses each destination module's *existing* create function (checklist items, goals, calendar events, reminders, gift ideas, projects, recipes) — no new create logic anywhere, the inbox only decides which existing one to call. Finance deliberately excluded (its own hard AI-exception nuance).
- [x] **Settings page** (`/settings`) — provider (Ollama/Claude) + live model picker (proxies Ollama's own `/api/tags`, never a hardcoded list) per task, plus the photo-strategy toggle.
- [x] **Inbox page** (`/inbox`) — paste box, multi-file photo upload, audio/video upload, and the review queue with generic editable-field rendering per proposal, a picker for checklist/person when the target needs one, and Confirm/Not-quite/Discard actions.

**Real gotchas hit and fixed during this build, worth remembering:**

1. **Ollama was bound to `127.0.0.1:11434` only** — unreachable from any Docker container via `host.docker.internal`, the exact same class of bug as the Postgres `127.0.0.1`-binding gotcha from Part B/C. Fixed with a systemd override (`/etc/systemd/system/ollama.service.d/override.conf`, `OLLAMA_HOST=0.0.0.0:11434`) + `ufw allow 11434/tcp`. Worth checking for any *future* native (non-Docker) service on this box too.
2. **`tesseract`/`ffmpeg` were installed on the LXC host, not in the `saga-api` container** — an easy mistake since Ollama genuinely does run natively on this box, but `saga-api` is containerized; a host-level `apt install` does nothing for it. Fixed by adding both to `saga-api/Dockerfile` directly. (The host-level installs are harmless leftovers, not used by anything.)
3. **`GET /inbox/media/:filename` initially sent no `Content-Type` header** — Fastify doesn't infer one from a raw stream. Added a small extension→MIME map.
4. **Cross-service calls in this project go through `host.docker.internal`, never Docker network service-name resolution** — each service (`saga-api`, `saga-web`, `ntfy`, now `saga-whisper`) is its own independent `docker compose` project, not on a shared network. `saga-whisper`'s URL had to be `http://host.docker.internal:8100`, matching `ollama.ts`/`ntfy.ts`'s existing pattern, not `http://saga-whisper:8100`.
5. **A real quality finding, not a bug**: fed a synthetic sine-wave tone through the voice pipeline as a plumbing test (no real recording available) — Whisper transcribed it as the single word "You", and `llama3.1:8b` **confidently fabricated an entire plausible-sounding fake recipe** from that one word rather than saying it couldn't extract one. Mechanically the pipeline worked end-to-end; the finding is that a local model will hallucinate a complete wrong answer rather than admit uncertainty — exactly the reason the whole feature is built around review-before-confirm rather than auto-adding anything.

**Defaults corrected same day, right after this landed:** Brandon flagged that a Claude API key is a real, separate cost — a paid Anthropic API key with its own billing, unrelated to a claude.ai Pro or Claude Code subscription (there's no way for a subscription's usage to authenticate a self-hosted app's own API calls; they're different products entirely). Every task now defaults to fully local/free out of the box: `recipe_photo_strategy` defaults to `ocr_then_structure` (was `direct_vision`), and `recipe_voice_structure` defaults to `ollama`/`llama3.1:8b` (was `claude`). The one exception, not a preference: `recipe_photo_vision_extract` still defaults to `claude`, but only because it's inert unless `direct_vision` is explicitly chosen, and no local vision model is pulled yet to make Ollama a working option there — not a cost default, a no-local-alternative-yet situation. Settings page copy now says plainly that Claude is a separate paid key wherever it's offered.

**A third provider added same day: Claude Code CLI run headlessly, authenticated via Pro/Max subscription (not a paid API key).** Brandon uses this exact pattern already (Claude Desktop, and Daniel Miessler's LifeOS project) and asked for it as the actual "last resort" instead of the paid API. Confirmed via research and a peek at LifeOS's own `.github/workflows/claude.yml` (not the whole repo — just the auth piece, as asked): the official mechanism is `claude setup-token`, run once on any device logged into the Pro/Max account, producing a long-lived token — this is the same env var (`CLAUDE_CODE_OAUTH_TOKEN`) Anthropic's own `claude-code-action` GitHub Action uses, not something improvised. Far simpler than building a custom "auth portal": no browser flow needed on the server at all, just an env var, same treatment as `ANTHROPIC_API_KEY`.

- [x] Claude Code CLI (`@anthropic-ai/claude-code`) installed globally in `saga-api`'s Docker image.
- [x] New `claude_cli` provider (`saga-api/src/lib/ai/claudeCli.ts`) — shells out to `claude -p <prompt> --output-format json`, with images passed via `--image`. **`recipe_photo_vision_extract` now defaults to `claude_cli`, not the paid API** — this is exactly the cursive-handwriting "last resort" use case, at no separate cost, matching Brandon's actual ask.
- [x] **Gotcha, real one**: my first pass added `--dangerously-skip-permissions` (reasoning: these prompts never need tool access anyway) — Claude Code's own **auto-mode safety classifier blocked the `scp` deploying that file**, flagged as "Create Unsafe Agents." Correct fix, and the safer approach regardless: `--disallowedTools "*"` blocks every tool outright rather than bypassing the permission system that gates them — same practical effect for a pure text/image-analysis call, but scoped-deny instead of blanket-bypass, and it didn't trip the classifier.
- [x] Settings page now offers three provider choices per task: Local (Ollama, free), **Claude via Pro/Max plan (free at point of use, your subscription's own limits)**, and Claude API (real separate cost, clearly labeled as such).

**`CLAUDE_CODE_OAUTH_TOKEN` — done 2026-09-20.** Brandon ran `claude setup-token` from his WSL Ubuntu CLI; one snag worth noting for next time: the browser auth page hands back an intermediate **authorization code** (`code#state` shape) that has to be pasted into the *terminal* where `setup-token` is waiting — not sent anywhere else — which is then exchanged for the actual long-lived token (`sk-ant-oat01-...` prefix) printed to that same terminal. Token is now in `saga-api/.env` on the LXC; live-tested via `docker exec saga-api-dev claude -p ... --disallowedTools "*"` and confirmed working end-to-end (clean JSON round-trip, no permission-classifier issues, `is_error: false`). Note: the CLI's JSON output always includes a `total_cost_usd`/`usage` field regardless of auth method — that's Claude Code's standard usage-accounting metric (what the call would cost under API pricing, for reference), **not an actual charge** when authenticated via a Pro/Max `setup-token`.

- [x] **Settings page token countdown** — new `CLAUDE_CODE_OAUTH_TOKEN_ISSUED_AT` env var (set to `2026-09-20`) + `GET /settings/claude-cli-token` (`saga-api/src/modules/settings/service.ts`) computes a flat 365-day expiry from it; shown on the Settings page as "N days left" (green → amber under 30 days → red if expired). Currently reads 365 days left, expires 2027-09-20.
- **Expiry research finding, not just an assumption**: official docs describe `setup-token`'s output as a flat one-year OAuth token with no documented inactivity-based early expiry. The only related expiry behavior found (24-hour access tokens needing silent refresh) applies to `/login`-based interactive sessions — a different credential type entirely, unrelated to this one. On that basis, **no keepalive cron was built** — nothing indicates one is needed for correctness.
- **Deferred, not built**: a "safety net" keepalive ping (a trivial scheduled `claude -p` call, just in case the above research turns out wrong in practice) — Brandon asked for this as a line item to pick up later rather than something to build now.

## Known gotcha carried over from the friend's stack doc

`host.docker.internal` resolves automatically under Docker **Desktop** (Mac/Windows). On plain Docker **Engine** on the `saga` LXC, it does not, by default. Every compose service that needs to reach a peer via `host.docker.internal` needs:

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```

This is already folded into [STACK-FOUNDATION.md](STACK-FOUNDATION.md) below, but flagging it here since it's the one thing in the original doc that would silently break on this box. (See Part B/C above for the follow-on gotcha this didn't fully cover.)
